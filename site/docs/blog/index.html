When the WAN drops: self-healing Kubernetes at the edge

Kubernetes needs its control plane to replace a lost Pod. edge-healer lets the nodes do it themselves when the control plane is out of reach.

Davide Lamagna

This is an informal write-up of the project report Edge-Healer: Decentralising Kubernetes with Edge Self-Healing. For the background, related work and references, please refer to the paper.

TL;DR

  • In Kubernetes, only the control plane can replace a lost Pod. If an edge site loses its WAN link, lost Pods stay lost until the link comes back.
  • edge-healer runs a small agent on every node. The agents gossip their free CPU, and when a Pod is lost while the API server is unreachable, the node with the most spare CPU recreates it locally.
  • When the link returns, the local changes are pushed back and duplicates are removed. The prototype restored Pods in a simulated four-node cluster with the API server cut off.

The freeze-brain problem

Kubernetes splits a cluster into a control plane and worker nodes. The control plane makes every global decision. The API server is the single front door to the cluster's state, which lives in etcd. The controller manager runs the loops that drive the cluster towards its desired state, such as "three replicas of this Pod". The scheduler decides which node each new Pod goes to. The workers just run what they are told.

This design is deliberate. It gives the whole cluster one consistent view, and in a data centre it works well. But it trades availability for consistency, and the trade becomes visible at the edge.

Picture a factory. Gateways and on-site devices run as Kubernetes nodes, managed from a cloud region over a thin WAN link that can drop for minutes at a time. During an outage, a Pod that crashes on a gateway is not replaced. Kubernetes never restarts a terminated Pod in place: a controller has to create a new one and the scheduler has to bind it to a node, and both sit on the far side of the broken link. The nodes are healthy but frozen, waiting for a brain they cannot reach. For a production line that cannot tolerate gaps of more than a few seconds, that is a real problem.

The goal: give every edge node just enough of a brain to detect a failure, agree with its peers on who should host the replacement, and start it locally, without the central control plane.

How edge-healer works

edge-healer is deployed as a DaemonSet, so every worker runs one copy. Each copy is a Pod with two containers:

  • a Serf sidecar (a Go binary) that keeps a gossip ring with the other nodes, and
  • the edge-healer agent, a Python operator built on Kopf that watches Pods and ReplicaSets and holds the bidding logic.

When a Pod disappears, this is what happens:

  1. Check the control plane

    The agent first asks the API server, with a one-second timeout. If the control plane answers, the agent does nothing and Kubernetes handles the loss as usual.

  2. Look at the gossip

    If the API server is unreachable, the agent looks at its map of free CPU, which the Serf sidecars keep up to date by gossiping each node's spare capacity.

  3. Bid

    Each agent compares its own free CPU with its peers'. If no peer has strictly more, it wins the bid.

  4. Bind optimistically

    The winner binds the Pod to its own node, recreating it on the spot without waiting for the scheduler or the ReplicaSet controller.

  5. Reconcile when the WAN returns

    Locally created objects are pushed back to the API server. If two nodes recreated the same Pod, the second bind is rejected and the duplicate is removed, so the cluster does not end up in a split-brain state.

The bidding rule is short enough to show in full. This is the core of src/scheduler.py:

peers = gossip.healthy_peers()          # {node: free CPU}, from Serf
my_cpu = peers.get(gossip.node, 0)
if any(cpu > my_cpu for cpu in peers.values()):
    return                              # lost bid: someone has more room
# won bid: bind the Pod to this node
await api.create_namespaced_pod_binding(name, namespace, target)

Two other pieces support it. A small SQLite cache keeps the desired ReplicaSet specs on each node, so the agent still knows what should be running after a reboot during an outage. And each agent exports Prometheus metrics: restore_latency_seconds, bind_conflicts_total and peer_updates_total.

You can watch the whole sequence, including a tie that produces a duplicate, in the interactive demo.

Why gossip

The agents need to share their state without a central coordinator, which is exactly what gossip protocols are for. Each node regularly sends its state to a few randomly chosen peers, and those pass it on. Updates spread like an epidemic.

Serf, which edge-healer uses, is built on SWIM (Das, Gupta and Motivala, 2002). SWIM detects failures by probing random peers and asking others to confirm when a probe fails. It piggybacks membership updates on those probe messages. Two properties make it a good fit for edge clusters. An update reaches every node in O(log n) rounds with high probability. And each node talks to a constant number of peers per round, so the total load grows only linearly with the cluster and there are no broadcast storms.

edge-healer uses Serf less for failure detection than for sharing resources: the payload that matters is each node's free CPU, which is what the bidding runs on.

How it differs from KubeEdge

KubeEdge is the industry-standard way to run Kubernetes at the edge, and it already keeps workloads running while the cloud link is down. The difference is in what happens when something new has to be created.

KubeEdgeedge-healer
ArchitectureHierarchical: EdgeCore on each node, CloudCore in the cloud as the single source of truthFlat: every node has an equal role in recovery once the WAN is cut

Recovery timeA lost Pod can stay down for minutes or hours, until the edge reconnectsTargeted at under a second after the loss is detected
ScalingRecovery load lands on CloudCoreEvery new node adds scheduling capacity as well as compute

Other projects tackle neighbouring problems. KubeFed manages fleets of clusters from a central federation plane, Liqo lets workloads roam between clusters, and Medik8s and Active-Monitor focus on node remediation and health checks. None of them coordinates replica rescheduling once the WAN is gone, which is the gap edge-healer aims at.

The experiment

The prototype ran on a simulated edge cluster: a four-node KinD (Kubernetes in Docker) cluster, with a control plane and three workers, each running the edge-healer DaemonSet. A small test Deployment, busybox-spread, put one replica on each worker. Each run followed the same workflow:

  1. Block the API

    An iptables rule drops all traffic to the API server on port 6443, simulating the WAN outage.

  2. Delete a Pod locally

    Inside a worker, crictl stops and removes the busybox containers, so the Pod disappears without the control plane being involved.

  3. Gossip and bid

    The sidecars keep exchanging free CPU; the agents detect the loss and run the bidding.

  4. Rebind and measure

    The winner rebinds the Pod. Prometheus collects the restore latency, bind conflicts and gossip updates.

In this first validation, edge-healer restored the Pods while the control plane was cut off. The logs showed each stage in order: the loss was detected, the agents gossiped and one of them won the bid and rebound the Pod. Once the API server was reachable again, the state was reconciled. The prototype also kept gossip traffic low on the three-worker ring.

The evaluation shows that the approach works, but it is not yet a full benchmark. The design aims to restore a Pod in under a second, against roughly two seconds for the standard path. Measuring that carefully, at larger scale, is part of the next steps.

Limitations and next steps

  • Rewrite the agent in Go. Go is the native language of Kubernetes. It would integrate better with the API machinery and cut the runtime overhead of the Python prototype.
  • Run on IoT-scale nodes. The goal is workers with less than 30 MB of RAM, which means a much smaller footprint.
  • Scale up. Clusters with dozens or hundreds of nodes would test how well the gossip and the optimistic rebinding hold up under CPU stress.
  • Stress-test WAN partitions. How long can the control plane stay unreachable before the nodes' decisions drift too far from the global state?
  • Compare with KubeEdge's offline mode on latency, correctness and resource use.
  • Package it as a Helm chart to make it easier to adopt and reproduce.

Reproduce the experiment

You need docker, kind and kubectl (client and server at most one minor version apart). From the root of the repository:

# 1. A KinD cluster: one control plane, three workers
cat <<EOF | kind create cluster --name serf-demo --config=-
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
  - role: worker
EOF

# 2. Build the agent and load it into the cluster
docker build -t edge-healer:latest src/
kind load docker-image edge-healer:latest --name serf-demo

# 3. Deploy the DaemonSet (agent + Serf sidecar on every node) and the test workload
kubectl apply -f config/rbac.yaml -f config/daemonset.yaml
kubectl -n kube-system rollout status ds/edge-healer
kubectl apply -f demo/busybox-spread.yaml

Then cut the API server off and remove a Pod from inside a worker:

# block the API server
sudo iptables -A OUTPUT -p tcp --dport 6443 -j DROP

# remove a busybox-spread Pod from inside a worker node
docker cp scripts/internal-pod-deletion.sh serf-demo-worker2:internal-pod-deletion.sh
docker exec serf-demo-worker2 bash -c 'chmod +x internal-pod-deletion.sh && ./internal-pod-deletion.sh'

# watch the bidding
kubectl -n kube-system logs ds/edge-healer -c healer --since=5s | grep "won bid"

# restore the API server
sudo iptables -D OUTPUT -p tcp --dport 6443 -j DROP

Each agent serves its metrics on port 8000 of its node:

curl -s http://<NODE_IP>:8000/metrics | grep -E 'restore_latency|bind_conflicts|peer_updates'

The README has more detail, including the online deletion path and the unit and integration tests.

The paper's abstract

Traditional Kubernetes relies on a highly consistent, centrally hosted control-plane, an assumption that breaks down in thin-WAN or intermittently connected edge deployments. When the API-server is unreachable, lost Pods remain unreplaced and production lines stall. We present edge-healer, a lightweight self-healing framework that decentralises recovery logic by running a Serf-backed gossip sidecar and a Python (soon Go) bidding agent as a DaemonSet on every worker node. Nodes periodically exchange free-CPU budgets and, upon detecting a missing Pod, issue a bind decision to recreate it on the best-suited peer—without waiting for the control plane’s scheduler or ReplicaSet controllers. The prototype is publicly available and shows that modest cluster-side changes can help achieve true edge autonomy while remaining API-compatible with upstream Kubernetes.
